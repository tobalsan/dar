PRD — Agentropy · Fully Self-Contained Agents (FSC)

Each robot carries its own recipe

The one-sentence big idea: today every agent is built from one shared kitchen in the code repo. Tomorrow, each agent folder will carry its own cooking instructions, build its own brain, and reboot itself — with no human help, ever.

01

Before vs. After

Right now, supporting 10 different agents means editing 2 shared files in the central code repo 10 separate times. One mistake can break all 10. Here's what life looks like today vs. what we're building toward.

😓 Today — shared kitchen, shared pain
  • 📂Agent A, B, C … all depend on one central dist/src/main.rs file in the repo.
  • ✏️Want a new mix of abilities? You hand-edit dist/Cargo.toml and dist/src/main.rs — every time, for every agent.
  • 🚫The built binary lives outside the agent folder. Moving an agent to a new machine means rebuilding from the central repo.
  • 🤝An agent can never update itself. A human or an external tool must stop it, rebuild it, and restart it.
repo/ ├── dist/ │ ├── Cargo.toml ← you edit this │ └── src/main.rs ← and this ├── extensions/ (shared) └── (all 10 agents share the same dist)
✅ Tomorrow — each agent owns its own backpack
  • 📦Every agent folder is fully self-contained. Move the folder to a new machine, run one command, and it's alive.
  • 🤖Each agent has its own extensions/ for custom abilities and its own .agentropy/ build recipe — auto-generated, never hand-edited.
  • ⚙️The built binary lives inside the agent folder at bin/agentropy.
  • 🔄The agent can rebuild and restart itself when its abilities change. Zero humans required after setup.
my-agent/ ├── agent.yaml ├── extensions/ ← your custom abilities ├── bin/ │ └── agentropy ← lives HERE now └── .agentropy/ ← auto-generated recipe ├── Cargo.toml ├── Cargo.lock └── src/main.rs
02

Layer 1 — The shared cookbook

This is Step 1 and the most important unlock. Without it, nothing else is possible. Understanding this layer is the main point of this document.

Layer 1

agentropy-cli — the shared cookbook

🍳

Analogy: Imagine 10 restaurants all sharing one handwritten recipe card in a single drawer. If someone spills coffee on it, every restaurant is stuck. The fix: print the recipe in a real cookbook that every restaurant keeps a copy of. Each restaurant still uses the exact same recipe — they just each have their own book to open.

Right now, all the startup logic — how the agent boots up, how it runs the doctor health check, how it dispatches work — lives inside dist/src/main.rs in the repo. It's one big handwritten card.

What we do: We lift all of that logic out of dist/src/main.rs and move it into a new reusable library crate (crate = Rust's word for a package or module) called agentropy-cli. Then both the repo's own binary and every agent's binary call the exact same agentropy_cli::run() function. They all read from the same cookbook.

Why this is the unlock: Once agentropy-cli exists as a library, any agent can depend on it. The self-update logic, the doctor health check, the build command — all of that comes along for free. An agent's own main.rs shrinks down to about 5 lines.
dist/src/main.rs — BEFORE (all the logic was jammed in here)
// hundreds of lines: boot wiring, doctor logic, CLI dispatch, etc.
// All of it lived here. Hard to reuse anywhere else.
dist/src/main.rs — AFTER (just 5 lines, calls the cookbook)
// This is the ENTIRE file now. Clean!
#[tokio::main]
async fn main() {
    agentropy_cli::run(plugins![
        tracker_files::extension(),
        runner_claude::extension(),
        // ... list of abilities
    ]).await
}
my-agent/.agentropy/src/main.rs — an agent's own main (also just 5 lines)
// Same shape. Different list of abilities. Same cookbook.
#[tokio::main]
async fn main() {
    agentropy_cli::run(plugins![
        tracker_files::extension(),
        runner_claude::extension(),
        my_custom_ext::extension(),  // agent's own ability!
    ]).await
}
Safety note: This refactor changes zero behavior. The logic moves to a new home, but it works identically. All existing tests stay green. It's like photocopying a recipe into a book — the food still tastes the same.
03

Layer 2 — The per-agent build recipe

Each agent gets its own .agentropy/ folder — a small auto-generated bundle that knows exactly how to build that specific agent's brain.

Layer 2

.agentropy/ — the agent's personal build recipe

🎒

Analogy: Think of .agentropy/ as the agent's backpack. Inside is a shopping list (Cargo.toml), a locked receipt with exact prices (Cargo.lock), a note pinning which oven to use (rust-toolchain.toml), and a short cooking script (src/main.rs). Everything needed to rebuild the agent — from scratch, on any machine — is in the backpack.

The .agentropy/ folder is generated automatically by running agentropy build --dir .. You never hand-edit it. Here's what it contains:

my-agent/ ├── agent.yaml ← the agent's config (you write this) ├── extensions/ │ └── my-custom-ext/ ← your custom ability (you write this) │ ├── Cargo.toml │ └── src/lib.rs ├── bin/ │ ├── agentropy ← the running brain (built binary) │ └── agentropy.prev ← backup brain, in case things go wrong └── .agentropy/ ← auto-generated, commit this! ├── Cargo.toml ← shopping list: which abilities to include ├── Cargo.lock ← locked receipt: exact versions (reproducible!) ├── rust-toolchain.toml ← which version of Rust to use └── src/main.rs ← 5-line cooking script (see Layer 1)

Key insight — "move folder = move agent": Because everything is inside the folder, you can zip it up and send it to a friend. They run agentropy build --dir my-agent and get an identical binary. No absolute file paths, no dependency on the original machine.

Reproducibility: The Cargo.lock file records the exact version of every piece of code used. Building with --locked means the result is bit-for-bit identical on every machine. Like a recipe with "use exactly 125g of flour" rather than "use some flour."
Shared build cache: When 10 agents all need the same standard abilities, they share a single compiled cache at ~/.cache/agentropy/target/. The common parts compile once. Changing one agent's custom ability takes only 1–3 seconds to rebuild.
04

Layer 3 — Auto-discovery of custom abilities

When you add a new custom ability to extensions/, how does the builder know to include it? It reads a tiny name-tag.

Layer 3

Discovery — the name-tag in every ability

🏷️

Analogy: Every ability crate (Rust package) in extensions/ wears a name-tag sticker. The builder scans the extensions/ folder, reads every name-tag, and auto-includes that ability in the recipe. No hand-editing required.

Each custom ability's config file (Cargo.toml) has a small extra section — the name-tag — that looks like this:

extensions/my-custom-ext/Cargo.toml — the name-tag section
[package]
name = "my-ext"
version = "0.1.0"

[workspace]  ← keeps this ability isolated from the main repo

[package.metadata.agentropy]
factory = "my_ext::extension"  ← THE NAME-TAG: "my factory function is here"

[dependencies]
host-api = { git = "https://github.com/agentropy/dar", rev = "abc1234" }

The builder scans extensions/*/Cargo.toml, finds all the [package.metadata.agentropy] sections, and uses them to auto-generate the agent's recipe. The scaffold command (cargo agentropy new my-ext --kind background) writes this name-tag automatically — you never even have to think about it.

Why not use a fancier trick (linkme)? We looked at a more "magical" auto-wiring approach called linkme where abilities would register themselves automatically at compile time. We rejected it: it still requires editing the shopping list (Cargo.toml) manually, it makes the code harder to read and debug, and it saved us essentially nothing. Explicit name-tags are boring, correct, and grep-able.
05

The self-update loop

This is the coolest part. A running agent can rebuild its own brain, health-check it, and hot-swap itself — all without stopping, and with a full safety net. A bad update can never brick the agent.

🛸

Analogy: Imagine a spaceship that can 3D-print a brand new engine while the old one is still running, test the new engine in a lab, and only then bolt it on and switch over — keeping the old engine in a drawer as a backup. If the new engine fails the test, the ship keeps flying on the old one. You never drift in space.

1

🔒 Lock

Grab a lock file (data/self-update.lock). If another self-update is already happening, wait. This prevents two rebuild attempts from stepping on each other.

safe: only one update at a time
2

📋 Regenerate the recipe

Scan extensions/* for name-tags. Rewrite .agentropy/Cargo.toml and .agentropy/src/main.rs to reflect the current set of abilities. If nothing changed, skip the whole build — no wasted work.

3

🏗️ Build the new brain (in the background)

Run cargo build --release --locked as a separate child process. The output goes to a temp file (bin/agentropy.new) — never over the live binary. The old agent keeps running normally the whole time.

old agent keeps running while building

⚠️ If build fails → log the error, release lock, keep old binary. Done.

4

🩺 Doctor health-check (the safety gate)

Spawn the new binary and run agentropy.new doctor --dir ... The doctor must successfully parse the config, load all abilities, and exit cleanly. This is the critical safety net.

new brain passes inspection before swap

⚠️ If doctor fails → delete agentropy.new, release lock, keep old binary. Done. The broken brain is thrown away.

5

🔄 Atomic swap

Rename bin/agentropy → bin/agentropy.prev (the old backup), then rename bin/agentropy.new → bin/agentropy. On Unix, this rename is atomic — it's a single instant flip with no gap where neither binary exists. The running process is completely unaffected because it's already in memory.

old binary saved as .prev backup
6

🚀 Restart into the new brain (execv)

execv (a Unix system call that replaces the current process's code with new code — same process ID, same memory address, instant swap) replaces the running code with the new binary. Same process, same PID, new brain. No external supervisor or service manager needed.

zero-downtime swap on Unix
↩

🛡️ Crash safety net (boot-time fallback)

At every boot, the agent runs a quick self-check. If the self-check fails and a bin/agentropy.prev backup exists, it immediately execvs back into the old backup. The agent keeps running no matter what.

fallback to .prev if new binary fails at boot
The safety guarantee in plain English: A bad update can never brick the agent because (a) the build must succeed, (b) the new binary must pass the doctor health check before any swap happens, and (c) even after a swap, the old binary is saved as .prev and the agent will fall back to it if the new binary fails at startup. At every step, if something goes wrong, the old brain wins.
06

Building it — 6 safe steps

The PRD defines a strict migration order. Each step keeps all tests green. You can stop after any step and have a working, shippable system. Step 1 is the starting point — it's also the most important.

01
Refactor dist → agentropy-cli library
Start here (c)
What we do

Move all boot/startup/CLI/doctor logic from dist/src/main.rs into a new library crate crates/agentropy-cli. The dist binary becomes a thin 5-line caller. No features change — just a code relocation.

Why it's safe

Zero behavior change. Every existing test must still pass. The repo's own binary builds and runs identically — it just routes through agentropy_cli::run() now. This is the unlock for everything else in this plan.

02
Add name-tags + update the scaffold
What we do

Add [package.metadata.agentropy] factory = "..." to the cargo agentropy new scaffold output. Update extensions/example (the reference example) to carry the marker. Define the pub fn extension() factory convention.

Why it's safe

The name-tag is a purely additive metadata comment inside Cargo.toml. Cargo ignores unknown metadata. No existing code changes behavior. Tests stay green.

03
Build the composer + init-build + build commands
What we do

Implement the ability-scanner + code-generator inside agentropy-cli. Add agentropy init-build --dir (bootstraps the .agentropy/ folder) and agentropy build --dir (regenerates + compiles + copies binary to bin/). Validate against the example-agent test fixture.

Why it's safe

These are new subcommands — they don't touch any existing functionality. Existing runs, tick loops, issue state, and all other behavior are completely unchanged.

04
Feature-gated subsetting of stock abilities
What we do

Make standard abilities (tracker, runner, dashboard, etc.) optional in the generated .agentropy/Cargo.toml. The composer reads agent.yaml to know which ones this agent actually needs, and only includes those. A minimal agent = a smaller binary.

Why it's safe

Only affects the generated file — the live system is unchanged until a new agentropy build is run. The default includes all standard abilities, so existing agents behave identically unless explicitly reconfigured.

05
Self-update loop, doctor gate, atomic swap, execv, .prev fallback
What we do

Implement agentropy self rebuild in agentropy-cli. Wire up the lock file, out-of-process build, doctor-gate spawn, atomic fs::rename swap, and execv restart. Add the boot-time self-check + .prev fallback in main(). This is the full self-update loop described in Section 5.

Why it's safe

The doctor gate is the primary defense — the live binary is never touched until the new one passes health checks. All the safety rails (lock, abort-on-failure, .prev backup) are built in from the start, not added later.

06
Off-box portability + lock refresh + optional offline vendor
What we do

Switch stock dependency references to git-pinned revisions (no absolute paths). Add agentropy lock-refresh for deliberate dependency bumps. Add optional --vendor flag to build/init-build for air-gapped machines with no internet.

Why it's safe

Portability is additive. The existing build path is unchanged. Git-rev references are more explicit than floating version ranges — they make it harder to accidentally break things.

07

Costs & gotchas

This plan is good, but not free. Here's what gets harder.

🔧

Rust toolchain required on every machine

Every machine that runs an agent must have cargo and rustc installed. This is a new operational requirement. The doctor command checks for this and gives a clear error message if it's missing: "cargo not found — install Rust via rustup."

🐧

Unix only (for now)

The atomic swap trick (rename(2) over a running binary) and the execv restart are Unix-specific. Windows works differently and is out of scope for this version. Windows support is a separate future project.

📦

Binary size varies by agent

Because each agent only links the abilities it actually uses (thanks to feature-gating in Step 4), a minimal agent's binary will be smaller than today's monolith. A fully-loaded agent is about the same size. Run the benchmark after Step 4 to confirm.

⏱️

First build takes a few minutes

The very first build downloads and compiles everything from scratch. After that, the shared cache at ~/.cache/agentropy/target/ means subsequent builds cost only 1–3 seconds for typical local changes.

🌐

Needs internet (unless vendored)

By default, cargo build fetches dependencies from GitHub and the registry. For machines with no internet (air-gapped), use agentropy build --vendor to bundle everything locally first.

💾

No Rust toolchain bundling

We considered shipping cargo + rustc inside the agent folder. That would add ~500 MB. Rejected. The toolchain must be installed on the host — this is the tradeoff we're accepting.

08

Glossary

Quick definitions for Rust/Cargo terms used in this doc.

crate
Rust's word for a package — a bundle of code with a name and version, like an npm package or a Python library. Can be a library (code others call) or a binary (a runnable program).
Cargo
Rust's build tool and package manager — like npm for JavaScript or pip for Python. Reads Cargo.toml (the shopping list) and Cargo.lock (the locked receipt) to build your code.
binary
The compiled, runnable program file — the thing you actually execute. Like an .exe on Windows. In this doc, the agent's brain lives at bin/agentropy.
plugin / extension
One self-contained ability that the agent can have — e.g., "knows how to talk to Linear", "knows how to run Claude", "knows how to show a dashboard". Each extension is its own crate.
doctor
A built-in health-check command (agentropy doctor --dir .) that verifies the agent config is valid, all abilities load correctly, and the toolchain is present. Think of it as a pre-flight checklist.
execv
A Unix system call that replaces the currently running program's code with a new program — same process ID, instant swap, no re-spawning. Used to restart the agent into its new binary without any gap in service.
linkme
A fancier auto-wiring trick we evaluated and skipped: it would let abilities register themselves automatically at compile time using a magic global list. Rejected because it still requires editing Cargo.toml manually, makes the code harder to debug, and saved us essentially no work. Explicit name-tags are better here.
workspace
Cargo's way of grouping multiple crates in one repo so they can share a build cache and settings. Local extension crates declare an empty [workspace] table to stay isolated from the main repo's workspace.
