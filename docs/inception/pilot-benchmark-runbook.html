Review verdict

A multi-agent review of PRs #1–14 against PRD-EXTRACTION.md found functional parity essentially complete. All 15 Linear slices (ALG-172–185 plus the gate itself) have been implemented; the PRD §16 checklist reads green on every dimension except ALG-186 itself, which is the benchmark being conducted here.

However, the footprint gate would have failed as-is. Six blocker classes were identified and patched before this benchmark run (see next section). A handful of lower-priority correctness issues were open at review time (section 3) and have since been fixed.

  • All 15 PRD slices implemented. Tracker, runner, orchestrator loop, retry / backoff, stall detection, HITL notifier, park barrier, Linear integration, webhook, dashboard, and export are all present and passing tests.
  • Footprint gate blocked by 6 classes of issues — Linear poll called twice per tick, per-slot full project scans, 1 Hz WebSocket polling, excessive Tokio thread count, unbounded SQLite growth, and over-featured Tokio dependency. All patched.
  • 8 correctness items subsequently fixed (section 3); all resolved after the benchmark review.

Env-var prefix mismatch in hooks. The before_remove kill-path exports AGENTROPY_* variables; all other hook execution paths export AIHUB_* (per PRD §5). Hook scripts that reference AIHUB_WORKSPACE on the remove path will silently receive an empty value.
orchestrator.rs:1651
All hook and runner child env vars unified to exactly AGENT_* prefix; AIHUB_* / AGENTROPY_* names retired; $AIHUB_HOME config expansion renamed $AGENT_HOME.
FIXED
Missing runs row on certain failure paths. When dispatch fails due to a hook error or a prompt render error, no row is inserted into the runs table. Those failures are invisible in dashboard history and are not counted by the park barrier.
orchestrator.rs:888
Hook, render, workspace, and spawn dispatch failures now insert a runs row with outcome dispatch_failed; visible in history and counted by the park barrier.
FIXED
Webhook rejects missing webhookTimestamp with HTTP 401. Additionally, issue-create events are filtered as irrelevant, so a newly created Todo issue does not trigger an immediate tick — the operator must wait for the next poll cycle.
dashboard/mod.rs:434
Missing webhookTimestamp accepted when HMAC is valid (timestamp checked only when present); issue-create events now treated as relevant and trigger an immediate tick.
FIXED

Stalled / needs_human now surface as "Interrupted"; terminal / released stay "Completed" (deliberate decision, diverges from PRD §8.4 by design).

Part A — Feature pilot

Work through the steps below in order. Steps A0 and A1 require no API spend and should be completed before any real-runner runs.

  1. A0

    Pre-flight

    Build the release binary and run the doctor check against the bundled fixture. Then reset the fixture so the run starts clean.

    cargo build --release
./target/release/agentropy doctor --dir ./example-agent

    Reset the fixture (do this before every run to avoid stale state):

    # 1. Reset all issues to todo
for f in ./example-agent/issues/*.md; do
  sed -i '' 's/^state: .*/state: todo/' "$f"
done

# 2. Clear workspaces (keep .gitkeep)
find ./example-agent/workspaces -mindepth 1 -not -name '.gitkeep' -delete

# 3. Delete the SQLite database
rm -f ./example-agent/data/store.db

# 4. (Optional) truncate the log
truncate -s 0 ./example-agent/logs/agent.log 2>/dev/null || true

    The SQLite database lives at <agent-folder>/data/store.db. The binary is at ./target/release/agentropy. Dashboard default port is 7878 (configured via dashboard.port in agent.yaml).

  2. A1

    Zero-cost smoke with the fake runner

    Copy example-agent to a scratch folder and switch the runner to fake. The fake runner is a built-in test shim that runs sh -c 'printf "%s\n" "$AGENT_PROMPT"' — it immediately exits zero after printing the rendered prompt. No Claude CLI, no API spend. 

    # Create scratch agent folder
cp -r ./example-agent ./scratch-agent

# Switch runner to fake in agent.yaml:
#   runner:
#     use: fake
sed -i '' 's/^  use: .*/  use: fake/' ./scratch-agent/agent.yaml

# Start the orchestrator
./target/release/agentropy run --dir ./scratch-agent

    Open the dashboard at http://127.0.0.1:7878/ and observe dispatch events appearing in real time. The fake runner completes each attempt with exit 0, but the issue file is not updated (the shim doesn't write it), so the orchestrator will classify the exit as a continuation retry (still-active issue after clean exit) and re-dispatch after 1 s. To stop the loop, set an issue's state: to done manually, or press Ctrl-C.

    Verify data in SQLite while the agent runs:

    sqlite3 ./scratch-agent/data/store.db \
  "SELECT run_id, issue_identifier, outcome, started_at FROM runs ORDER BY started_at DESC LIMIT 10;"

sqlite3 ./scratch-agent/data/store.db \
  "SELECT event_id, run_id, issue_identifier, kind, payload FROM events ORDER BY event_id DESC LIMIT 20;"

sqlite3 ./scratch-agent/data/store.db \
  "SELECT claim_id, run_id, issue_identifier, claimed_at, released_at FROM claims ORDER BY claim_id DESC LIMIT 10;"

    Confirm: run rows land in the runs table; event rows accumulate in events; each claim has a released_at timestamp after the run completes; outcomes are recorded correctly.

  3. A2

    Real-runner single-issue run

    Warning: this step spends API budget. Ensure the Claude CLI is installed and authenticated (claude --version) before proceeding. Use example-agent with its default claude-code runner. 

    ./target/release/agentropy run --dir ./example-agent

    Verify the following:

    • The issue file transitions state: todo → state: in_progress → state: done as the agent works.
    • The dashboard at http://127.0.0.1:7878/ shows live run state updates (active run, elapsed time, last event).
    • After the run completes, kill the orchestrator (Ctrl-C) and relaunch. The dashboard history panel should show the completed run — confirming SQLite persistence survives restarts.
  4. A3

    Linear tracker pilot (optional but recommended)

    Create a scratch Linear project and initialize a WORKFLOW.md seeded with its frontmatter. Requires a valid LINEAR_API_KEY in the environment. 

    export LINEAR_API_KEY=lin_api_XXXXXXXXXXXX

# Scaffold WORKFLOW.md with Linear frontmatter
./target/release/agentropy init-workflow \
  --dir ./linear-agent \
  --linear-project-slug YOUR_PROJECT_SLUG \
  --linear-project "Your Project Name" \
  --expose-graphql-tool

# Validate the config
./target/release/agentropy doctor --dir ./linear-agent

# Run
./target/release/agentropy run --dir ./linear-agent

    The init-workflow command writes a WORKFLOW.md frontmatter block with tracker.kind: linear, tracker.project_slug: <slug>, and linear.exposeGraphqlTool: true. Polling is controlled by orchestrator.poll_interval_ms in agent.yaml.

    Simulate a stall. Set runner.stall_timeout_ms to a short value (e.g. 5000 ms) in agent.yaml and use use: fake so the runner never writes a terminal state. The orchestrator will detect the stall via the stall_timeout_ms threshold, move the issue to the Needs Human state, and emit a HITL notification to stdout (default notifier).

Part B — Performance benchmark (ALG-186)

All steps use the fake runner unless stated otherwise. No API spend required for the benchmark itself. Record all measurements in the table at the end of this section.

  1. B1

    Single-instance idle baseline

    Launch one agentropy instance with no Todo issues (so it is polling but never dispatching). Sample resource usage every 30 seconds for at least 10 minutes and write to a log file. 

    # Set all example-agent issues to done so the orchestrator idles
for f in ./example-agent/issues/*.md; do
  sed -i '' 's/^state: .*/state: done/' "$f"
done
sed -i '' 's/^  use: .*/  use: fake/' ./example-agent/agent.yaml

# Launch in background
./target/release/agentropy run --dir ./example-agent > ./example-agent/logs/agent.log 2>&1 &
AGENT_PID=$!

# Sample every 30s for 10+ min (20 samples = 10 min)
for i in $(seq 1 20); do
  ps -o pid=,rss=,%cpu=,etime= -p "$(pgrep -d, agentropy)" 2>/dev/null \
    | awk -v ts="$(date +%s)" '{print ts, $0}' | tee -a footprint-b1.log
  sleep 30
done

kill $AGENT_PID 2>/dev/null

    Expected results: RSS in the tens of MB; %CPU ≈ 0 between ticks; no growth trend over the 10-minute window.

    Reference measurement (post-fix smoke run, June 10 2026, idle fake-runner instance, 60 s uptime): RSS 14.9 MB, CPU 0.0%, 5 threads, clean SIGTERM shutdown. Extrapolated fleet of 10 ≈ 150 MB total — comfortably inside the 8 GB gate.

  2. B2

    10-instance fleet baseline

    Stamp out 10 agent folders from a template, each with a distinct dashboard port, and launch them all. The dashboard port is configured via the dashboard.port field in agent.yaml. 

    # Create 10 agent folders with ports 7879..7888
for i in $(seq 1 10); do
  PORT=$((7878 + i))
  DIR="./fleet/agent-$i"
  cp -r ./example-agent "$DIR"

  # Switch to fake runner and set all issues to done (idle fleet)
  sed -i '' 's/^  use: .*/  use: fake/' "$DIR/agent.yaml"
  for f in "$DIR/issues/"*.md; do
    sed -i '' 's/^state: .*/state: done/' "$f"
  done

  # Set distinct dashboard port
  sed -i '' "s/^  port: .*/  port: $PORT/" "$DIR/agent.yaml"

  # Launch
  ./target/release/agentropy run --dir "$DIR" \
    > "$DIR/logs/agent.log" 2>&1 &
  echo "Launched agent-$i on port $PORT (PID $!)"
done

# Sample fleet RSS + CPU every 60s for 60+ min (61 samples)
for i in $(seq 1 61); do
  PIDS=$(pgrep -d, agentropy 2>/dev/null)
  [ -z "$PIDS" ] && echo "No agentropy processes found" && break
  ps -o pid=,rss=,%cpu=,etime= -p "$PIDS" 2>/dev/null \
    | awk -v ts="$(date +%s)" '{print ts, $0}' | tee -a footprint-b2.log
  sleep 60
done

# Shut down fleet
pkill agentropy 2>/dev/null || true

    Pass criteria: Total RSS across all 10 processes leaves comfortable headroom on an 8 GB machine; per-process idle RSS is in the tens of MB; %CPU ≈ 0 across the fleet.

  3. B3

    Memory flatness under churn

    Run the fleet with the fake runner and a feeder loop that continuously re-adds Todo issues, so the orchestrator cycles through dispatch → completion → re-dispatch without stopping. Compare RSS at t=0 vs t+1h to confirm memory is flat (no leak). 

    # Feeder loop: reset one issue to todo every 5s so the agent always has work
FEEDER_DIR="./fleet/agent-1"
while true; do
  ISSUE=$(ls "$FEEDER_DIR/issues/"*.md | head -1)
  sed -i '' 's/^state: .*/state: todo/' "$ISSUE"
  sleep 5
done &
FEEDER_PID=$!

# Record RSS at start
T0_RSS=$(ps -o rss= -p "$(pgrep -d, agentropy)" 2>/dev/null | awk '{s+=$1} END {print s}')
echo "t0 total RSS: ${T0_RSS} kB" | tee churn.log

# Wait 1 hour
sleep 3600

# Record RSS at end
T1_RSS=$(ps -o rss= -p "$(pgrep -d, agentropy)" 2>/dev/null | awk '{s+=$1} END {print s}')
echo "t+1h total RSS: ${T1_RSS} kB" | tee -a churn.log

kill $FEEDER_PID 2>/dev/null

# Check SQLite to confirm heartbeat pruning is working
sqlite3 "$FEEDER_DIR/data/store.db" \
  "SELECT COUNT(*) AS heartbeats FROM heartbeats;"
sqlite3 "$FEEDER_DIR/data/store.db" \
  "SELECT COUNT(*) AS events FROM events;"
sqlite3 "$FEEDER_DIR/data/store.db" \
  "SELECT COUNT(*) AS runs FROM runs;"

# Check DB file size
du -h "$FEEDER_DIR/data/store.db"

    Pass criteria: RSS at t+1h is within a few MB of t=0. Heartbeat row count stays bounded (pruning active). Event row count grows proportionally with run output — not unboundedly.
