Extension architecture & footprint

Agentropy
Can a minimal core + plugins survive Rust's footprint promise? — feasibility note

Yes, it's possible. But two surprises drive the whole design:

1. "Minimal core that loads plugins" is the opposite of "minimal footprint." A runtime plugin host is more code than a tuned monolith. The smallest binary comes from compiling only what you use, not from a generic loader.

2. Footprint isn't your constraint anyway. The claude/codex child process outweighs your runtime by 10–50×. Whether your core is 15 MB or 50 MB is noise next to one LLM subprocess. Choose your transport on portability and sandboxing, not bytes.

Why naive "drop in a .so" doesn't work in Rust

Your instinct — "Rust's power is compiling everything into one binary" — is right, and it's exactly why dynamic plugins are awkward. Rust has no stable ABI: the way Rust lays out types and function calls in memory can change between compiler versions. A plugin compiled today may not safely link against a core compiled tomorrow. C/C++ have a frozen ABI; that's how Chrome and VSCode-native modules work. Rust deliberately doesn't, in exchange for optimization freedom.

So clean in-process native plugins (dlopen + Rust types) are fragile and not recommended. That leaves three real ways to be "extensible," each with a different footprint profile.

Mechanism What it is Footprint cost Drop-in?
Cargo features Compile-time on/off switches (--features discord,github). Unused code is stripped by the linker — truly zero-cost. Best. Pay only for compiled features. No — recompile
WASM (wasmtime) Portable sandboxed modules loaded at runtime from the agent folder. Rust→WASM is solved. Small. Host ~few MB shared across all plugins; each plugin <1 MB. Yes
Subprocess Each extension is its own process; talk over stdio JSON-RPC (MCP-style). Any language. Multiplies. +5–15 MB RSS per Rust ext; 4–10× that for Node/Python. Yes
Tension

The "minimal binary that just loads extensions" dream pushes you toward WASM/subprocess. But a wasmtime host adds megabytes of code your current 8.2 MB monolith doesn't carry. You don't get smaller by adding a loader — you get more portable and swappable. Be clear which one you actually want.

Footprint, concretely

Your measured baseline: idle instance 14.9 MB RSS, binary 8.2 MB (per the pilot runbook). Here's what each architecture does to that, per agent, before the LLM child:

Architecture Core RSS (idle) Notes
Today — monolith ~15 MB Everything compiled in. Your current state.
Monolith + cargo features ~10–15 MB Smaller if you drop unused trackers/runners. Lowest possible.
+ WASM host (wasmtime) ~20–30 MB Host code + a few resident plugins. Lazy tools cost 0 until called.
+ Subprocess channels ~30–55 MB Each persistent channel (Slack/Discord WS) is its own process.
LLM child (claude/codex) 150–600 MB+ The real cost. Dwarfs every row above.
Read

Even the heaviest extension architecture (~55 MB) is a rounding error against one LLM subprocess. Your 8 GB / 10-instance gate is decided by how many LLM children run at once, not by your plugin host. Footprint does not veto this design.

Recommended: hybrid, transport-per-type

Don't pick one transport. Match each of your four extension categories to the transport that fits its needs. The core defines a small capability vocabulary; the manifest declares runtime: feature | wasm | subprocess; the host routes accordingly.

Category Best transport Why
Runner
claude / codex / opencode		 Feature or thin WASM These spawn a subprocess anyway. The adapter is tiny glue logic — build/arg/parse. No reason to pay a second process for it.
Tracker
linear / github / files		 WASM HTTP poll + JSON parse. Pure, portable, sandboxable. Third parties can ship a tracker as a single drop-in .wasm. Your Tracker trait is already the seam.
Channel
discord / slack / telegram		 Subprocess / native Long-lived TLS WebSockets + heavy SDKs. WASM sockets aren't mature on stable wasmtime. This is the one case where a separate process earns its RSS.
Generic
web chat / TUI / admin		 In-core or WASM ui.panel UI fragments served by the core, or compiled-in for the dashboard you already have.

What "the core" actually keeps

  • The tick loop (reconcile → collect → dispatch → publish) — this is the irreducible product.
  • The two-state invariant (issue state owned by tracker, run state owned by orchestrator). Don't let plugins blur this.
  • Path containment, secret resolution, the capability vocabulary, and the plugin host.
  • A small frozen verb set per category — e.g. tracker = poll_candidates / fetch_states / fetch_terminal (+ optional writes). Adding a tracker = new plugin, zero core change. Adding a verb = deliberate core change.
Note

You've already started this. The read-only Tracker trait and the split runners are compile-time extensions. The migration is: lift those traits into a stable capability ABI, add a manifest + loader, and move the network-heavy/swappable ones out to WASM or subprocess. The orchestration loop barely changes.

If footprint isn't the driver, what is?

Decide the design on these, in order — they matter far more than RSS:

  • Drop-in without recompiling? If yes → you need WASM or subprocess. If "recompile is fine for first-party," cargo features alone get you a swappable monolith for free.
  • Third-party / untrusted extensions? If yes → WASM (real sandbox) or subprocess (OS sandbox). Cargo features can't sandbox.
  • Self-containment tenet (move the folder, move the agent). Favors WASM — one portable artifact, no per-arch native builds. Native channels break cross-platform tar unless you ship multi-arch.
  • Dev velocity. Cargo features > WASM > subprocess for authoring speed of first-party code.

Suggested staging

v1  Trait + cargo-feature registry. Formalize the seams you already have.
    Smallest binary, swap-by-recompile. Proves the verb set is right.

v2  Add WASM host for trackers + tools (drop-in, sandboxed, portable).
    This is where "git clone the folder = working agent" lands.

v3  Subprocess channels (Slack/Discord) once you want them.
    Per-agent tokens, opt-in, zero RSS when disabled.

If at v1 you can add a tracker or runner without touching the loop, the abstraction holds. If either forces a core change, the verb set is wrong — fix that before adding any runtime loader.
