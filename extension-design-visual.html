Agentropy · extension architecture

How extensions work,
drawn out.

The core is a tiny host that knows nothing about your domain. The orchestrator, the scheduler, channels — all sit on top as extensions, each in its own repo. Here's the whole idea in boxes and arrows, with plain-English for the words that tripped you up.

0

Two words first

"Trait" and "Issue model" lost you. They're simple, and everything below rests on them.

trait
A checklist of abilities. A contract.

"To count as a Runner, you must be able to execute a turn." Anything that can is a runner, as far as the host is concerned. A job description — the host doesn't care who you are, only that you can do the job.

Issue model
One standard shape for a task.

Linear, GitHub, Jira each describe a task differently. The Issue model is the single shape they all translate into: identifier, title, state, priority… A shipping container — contents differ, the box is the same size. (Lives only in the tracker contract, not the host.)

1

The core is a host, not the loop

The orchestrator is not the core. The core is generic plumbing that knows zero domain concepts — not even "Issue." It provides services; extensions use them. The orchestrator is just the first extension on top.

2

Three roles, one question

Every piece is one of three things. The deciding question: does anything call into you through a typed contract?

Twist

The orchestrator is a plain extension that consumes cap-tracker + cap-runner. So capability crates flow two ways: providers implement them (github tracker), consumers call them (orchestrator). Plain features touch neither.

3

Cardinality — one runner, many channels

Capabilities differ in how many run at once. This is what "swappable" got wrong: channels don't replace each other, they coexist.

CapabilityActive at onceMeaning
runnerexactly 1The agent runs one runner at a time (claude or codex).
tracker1 (N later)Orchestrator polls one configured tracker. More is possible, not needed now.
channelN concurrentEvery configured channel is live. Reachable from all of them simultaneously.
plainN independentRun as many as you configure; each does its own thing.
4

Contracts & the standard shape

A capability is a contract the caller talks to without knowing who fills it. Trackers also agree on the Issue shape they hand back.

5

Every piece is its own repo

Your real goal. The contract crates are tiny and shared; everyone depends on them and on nothing else. Arrows mean "depends on."

6

Pick · build · run

Each extension raises its hand with one line. A thin dist repo names the mix you want; cargo build drops only those into one binary. That's your recompile step.

// inside any extension repo — its whole "register me" cost:
inventory::submit! { Plugin { id: "github", role: Tracker, make: || Box::new(GithubTracker::new()) } }

At runtime — the bus is the spine

Net

Separate repos ✓. Independent versioning ✓. Any extension type, not just orchestration ✓. Smallest footprint ✓. Price: one cargo build on a mix change. Linchpins: keep host-api and each cap-* tiny and stable.
